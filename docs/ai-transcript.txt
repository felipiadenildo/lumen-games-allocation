  dollar to a side (BR Games or US Games) and records who booked it and which

  - the allocation table;
  - a summary by booked group × side, for each month and for the quarter;
  - data quality checks that run with the pipeline, plus reconciliation;
  - a one-page Tax note;
  - a README;
  - the AI transcript or log;

  communication" ahead of polish. Finding data issues is stated as part of the
  task, and each issue needs a dollar impact. Then there is the interview:
  running the solution, a live change, a code review and a business partner
  question. Readable, data-driven code matters as much as the result.

  # Design

  ## Rules

  ### R1. Scope
  - **Rule:** every ledger line is in scope except lines whose account group is
  Depreciation and lines whose amount is 0. Credits (negative amounts) stay in
  scope.
  - **Check:** in-scope + out-of-scope = all ledger lines, in count and in
  dollars. Every out-of-scope line is in the output with its reason
  (depreciation or zero_amount); schema in F3.

  ### R2. Booked entity and booked group
  - **Rule:** the booked entity is the line's entity. The booked group is that 
  entity's entity_group in entities.csv.
  - **Check:** every in-scope line has a booked group.

  ### R3. Cost type comes from the department
  - **Rule:** the cost center's department decides the path. Live Games and New
  Games are direct. Engineering, Marketing, People and Operations are indirect.
  - **Check:** every in-scope line has exactly one cost type, or is unallocated
  with a reason.

  ### R4. Direct, single game
  - **Rule:** a direct cost center with a game sends 100% of the line to that
  game.
  - **Check:** share = 1 for these lines.

  ### R5. Direct, pool
  - **Rule:** a direct cost center with a pool_id splits the line across the 
  pool's games with fte > 0 in that month. share(game) = fte(game, month) / sum 
  of fte of the pool's games with fte > 0 in that month.
  - **Check:** for each line, shares add up to 1. Only games in the pool receive
  dollars. Games with fte = 0 or no fte that month get nothing.

  ### R6. Direct, bearing group
  - **Rule:** a direct cost does not change entity. Bearing group = booked 
  group.
  - **Check:** for every direct row, bearing group = booked group.

  ### R7. Direct, side
  - **Rule:** the side comes from the game's mapping row valid that month (R10).
  By entity resolves to BR Games when the booked entity is LGB, and to US Games
  for any other entity.
  - **Check:** every direct row ends with BR Games or US Games. By entity never 
  appears in the output.

  ### R8. Indirect, buckets
  - **Rule:** an indirect line is split across buckets by each bucket's share of
  the month's employees. A bucket is the first word of the employee's category 
  in lower case, an underscore, and the employee's entity group in lower case, 
  e.g. live_br. share(bucket) = employees in bucket that month / all employees
  of the company that month.
  - **Check:** for each month, bucket shares add up to 1. Each indirect line's
  rows add up to the line's amount.

  ### R9. Indirect, bearing group and side
  - **Rule:** both come from the bucket's mapping row valid that month (R10).
  - **Check:** every indirect row has a bearing group and a side.

  ### R10. Mapping rows have dates
  - **Rule:** a mapping row applies to a month when the month's first day is
  between start_date and end_date, both inclusive.
  - **Check (on the inputs, before the join):** for each game or bucket used in
  a month, exactly one mapping row applies.

  ### R11. Reconciliation and summary (from "What to deliver", items 2 and 3)
  - **Rule:** ledger total = out of scope + allocated + unallocated, for each
  month and in total. The summary shows the amount by booked group × side, for
  each month and for the quarter. The quarter is the sum of the months.
  - **Check:** the equation holds with abs(difference) < 0.005. Summary total =
  allocated total.

  1. Technology

  pandas only
  - + Same tool as the notebook: reuses its loading code and reasoning, one
    language to explain.
  - + Checks and the run log fit naturally in Python, and printing intermediate
    tables is easy when the team asks "show me".
  - − Merges, group-bys and share math in pandas read less like the BRIEF's
    rules than SQL does. Index and dtype surprises are a common source of live
    bugs.
  - − A reviewer has to follow chained method calls, which is harder to read
    aloud.

  DuckDB SQL, Python only running it
  - + The allocation reads close to the rules ("join pools, divide fte by the
    sum over the pool"), which a non-Python reader can follow.
  - + Each step is a query you can run and inspect on its own. Joins that
    multiply rows are easy to spot with a count(*).
  - − Moves away from the notebook, so you'd re-implement loading and checks you
    already wrote in pandas.
  - − Check messages, logs and exit codes still need Python, so in practice it's
    partly a mix anyway. Adds one dependency.

  Mix: pandas for loading and checks, SQL for the allocation
  - + Keeps the notebook's checks as they are and gives the allocation the
    readability of SQL.
  - + The split matches the design: checks guard the inputs, and SQL applies the
    rules.
  - − Two languages to explain and switch between during a live change.
  - − You have to decide where trimming, typing and joins happen. If both sides
    do it, rules get duplicated or drift apart.

  2. Code structure

  One Python file, a function per step
  - + Everything in one place, so finding where a rule lives during a live
    change is quick.
  - + No imports between modules or packaging. Easy to run from a clean
    checkout.
  - − It can grow long once checks, the allocation, the summary and output
    writing are all in it.
  - − Testing steps separately depends on discipline, since nothing enforces
    boundaries.

  Numbered SQL files, one per step, plus a small runner
  - + The order of steps is visible in the file names, which works as a map for
    the code review.
  - + Each file maps to one rule or step, and a live change touches one small
    file.
  - − The runner and how it passes tables between steps is extra code you have
    to explain.
  - − Errors point to a SQL file rather than a Python line, so debugging live is
    less direct.

  Small Python package
  - + Clear separation (load, checks, allocate, output) and room for tests.
  - − More files and imports than about 2,000 rows need. It conflicts with "no
    abstractions we don't need".
  - − Packaging and install steps add things that can break in the
    clean-checkout test.

  dbt
  - + Built-in tests, dependency graph and docs, all familiar to analytics
    teams.
  - − Heavy setup (profiles, adapter, project config) for a one-month,
    eight-file job, which makes the clean-checkout test riskier.
  - − Templated SQL is harder to read aloud and change live. The "how to run"
    section of the README gets longer.
  - − Signals tooling over reasoning, which the evaluation weighs less.

  3. Where unallocated and out-of-scope dollars live

  One table with every ledger line and a status column
  - + Reconciliation is one group-by on status, and every dollar is in one place
    (R11).
  - + Satisfies R1's check directly, since out-of-scope lines are in the output

  - − Mixes grains. An allocated line has one row per game or bucket, while an
    out-of-scope line has one row. Totals by status must be summed carefully.
  - − Every consumer, including the summary, has to filter on status. If someone

  Allocation table plus a separate out-of-scope file
  - + The allocation table stays one grain (line × destination), with
    unallocated rows as a status inside it.
  - + Out of scope is clearly "not part of the answer" and is still in output/.
  - − Reconciliation needs two files. The equation in R11 must say which file
    holds which term.
  - − Unallocated still sits next to allocated rows, so the filtering risk is
    the same as above, only smaller.

  Three separate files (allocated, unallocated, out of scope)
  - + Each file has one meaning. The summary reads only the allocated file and
    can't include the wrong dollars.
  - + Easy for Tax to open "unallocated" and see what needs their input.
  - − Reconciliation joins three files, and a line split partly allocated and

  4. What a blocking check does

  Write nothing new, keep the old files
  - + output/ always holds a complete, consistent run.
  - − The old files no longer match the inputs, and someone may read them as

  - − There is no checks file explaining the failure unless it is written
